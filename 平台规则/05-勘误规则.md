# 勘误规则（三类）

平台有三类"勘误"，流转不同。分别按 `api/bugs.py`、`api/datasets.py`、`api/code.py` 实现书写。

## 一、原始数据勘误（最复杂，`api/bugs.py`）

对象：数据集某条记录某变量的取值。**含历史/评分/自动改数**。

流程：
1. 提交：单条 `POST /datasets/{slug}/bugs`，或批量 `POST .../bugs/batch`（Excel/CSV，先下 `bug-template`）。
   前端统一从「勘误上传」进入，再选单条/批量。无论哪种方式，都集成为**一条 Bug + 多个 BugItem**
   （子项含 `唯一ID值/变量名/当前值/建议值/说明/证据/是否新增官员`）；说明和证据文字均必填，附件可选。
   批量模板的「说明」「证据」必须分列，旧的「说明与证据」合并模板会被拒绝并提示重新下载。
2. 唯一 ID 校验：单条用 `GET .../bugs/id-check`，批量先用 `POST .../bugs/batch/validate`。
   校验基于最新原始版本和数据处理设置中的唯一 ID：恰好匹配一条才直接通过；重复匹配阻止提交；零匹配时须明确
   确认「新增官员」。新增官员只作提示和人工处理标记，系统不自动追加字段不完整的空记录。
3. 列表：按上传时间倒序，支持 `pending/accepted/fixed/rejected`（未确认/已采纳未修改/已采纳已修改/未采纳）
   和近 7 日/近 30 日/不限日期筛选。旧记录无可靠 `created_at` 时只进入“不限日期”，显示“历史时间未知”。
4. 打分：人工 `POST /bugs/{bid}/reviews` 的评分理由必填，同一用户再次提交会更新原评分，人数按不同人工用户计。
   AI 用 `POST /bugs/{bid}/ai-review` 或 `/bug-items/{iid}/ai-review`，必须同时读取说明、证据、当前值、建议值，
   返回 0–10 分和理由；AI 未启用或输出不可解析时不保存默认分。
5. **终审**：`POST /bugs/{bid}/finalize` 或 `/bug-items/{iid}/finalize`，`adopt_level ∈ (full|partial|reject)`；
   非 reject → `accepted`，reject → `rejected`。父 Bug 状态按子项聚合。
6. **自审规则（八节 4）**：`self_review = (reporter == 当前管理员)`；若该数据集**还有其他管理员**，本人提交的勘误
   **必须由另一名管理员终审**（否则 403）；只有一名管理员时允许自审并写审计 `self_review`。
7. 应用改数：先由 `GET /datasets/{slug}/corrections-release-preview` 返回人可读摘要、实际 Stata 代码、
   自动/人工条数和 `preview_hash`。管理员可复制或下载 `.do`；一键执行必须带回该 hash，预览后集合变化即拒绝。
   自动执行在任何写入前整批检查唯一匹配和当前值，任一不符便原子中止。新增官员项不自动执行，继续保持
   `accepted`；其余成功项标 `fixed` 并同步父勘误。管理员手工修改后普通发版并勾选勘误，也会同步子项状态。

采纳会给报告人按终审分加贡献；评审方向与终审一致者 +k。

旧表字段迁移：`a6b7c8d9e0fb` 给 `bugs` 增加可空 `created_at`，给 `bug_items` 增加可空 `evidence`
和默认 false 的 `is_new_officer`；历史时间不回填，避免伪造上传日期。

## 二、Codebook / 对照表 勘误（简单，`api/datasets.py`）

对象：某版本的 codebook 或对照表文件。**刻意做简单：不记历史版本迭代**。

流程（`FileCorrection` 表）：
1. 成员提交：`POST /datasets/{slug}/file-corrections`（`target ∈ codebook|mapping` + 文字内容）。前端在版本库每个文件旁的「报错」入口。
2. 管理员查看：`GET /datasets/{slug}/file-corrections`（管理员看全部、成员看自己提交的）。进消息中心待办。
3. 采纳/驳回：`POST .../file-corrections/{fid}/decide?approve=` → `accepted` / `rejected`
   （与原始数据勘误一样的"确认采纳"动作，但没有评分、没有自动改文件、没有版本迭代）。

## 三、处理代码勘误（`api/code.py`）

对象：处理代码脚本。两种：
- **评论式勘误**：`POST /code/{cid}/comments`（`is_correction=True` 标记为勘误类评论）。
- **代码 Bug**：`POST /code/{cid}/bugs` → `POST /codebugs/{bid}/reviews` → `/codebugs/{bid}/finalize`。
代码本身走版本迭代（`code_versions`，发布必须写 changelog），作者可 `POST /code/{cid}/grants` 授予他人"可改/可重发布"。

## 四、共同点

三类勘误的"是否采纳"都由**数据集管理员**拍板；都会进消息中心待办（见 `07`）。区别在于：只有**原始数据勘误**有
评分制、自动改数与版本联动；文件勘误与代码评论式勘误是轻量确认。
